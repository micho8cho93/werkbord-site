# werkbord site

The launch page for [werkbord](https://github.com/micho8cho93/werkbord): a headline, a beta waitlist, and a working demo of the app. Plain HTML, CSS and JavaScript. No build step and no dependencies, so it runs as-is on GitHub Pages.

- `index.html`: the page. The headline and subheader, the waitlist, and the demo. From 1200px in landscape the page fits one screen with no scroll: the copy on the left, and on the right a Desktop and Phone switch that shows one simulator at a time, the desktop window or the phone in an iPhone frame. The headline and the simulator scale with the screen. From 768px to 1199px, and in portrait, the same parts stack and the page scrolls. Below 768px the site is two pages. The first fits the screen with no scrolling (it was checked from 320 by 568 up): the header holds the logo and Try the demo on opposite sides, and under it are the headline, three points of one line each (the text is sized to the column, about 10px on a 390px phone), and the waitlist. Try the demo opens the second page, which opens on the card that says what werkbord is, with Back in its bar; Start walkthrough there begins the guided demo, and I'll explore opens the phone app full screen with no guide. The choice is remembered for the browser tab, so Try the demo goes straight in after that.
- `404.html`: sends visitors home.
- `assets/css`: `site.css` (tokens from the identity sheet, buttons, header, footer), `app.css` (the app replica), `pages.css` (the page layout, the headline, and the iPhone frame), `waitlist.css` (the waitlist block).
- `assets/js`: `common.js` (helpers shared by the demo), `demo-guide.js` (draws the guided demo's note, its ring and its line, and keeps them in place), `demo-motion.js` (the app's motion for both simulators: cards that travel, layers that arrive and leave, charts that grow, Salie's fading words and live pixel mark), `app-demo.js` (the app replica: the desktop window with Universal, Individual and a Team, and the phone with its Control Deck; they share one controller, and Salie offers only predefined messages with scripted replies), `demo-view.js` (the Desktop and Phone switch, the quick actions, and the full-screen phone below 768px), `rolodex.js` (the rotating word in the headline), `waitlist.js` (the email waitlist).
- `assets/img`: the mark in light and dark, the favicon, `og.png` (the 1200 by 630 share image), and `app/overview-light.webp` (the picture shown to visitors without JavaScript).
- `docs/waitlist-schema.sql`: the waitlist database schema and its functions.
- `llms.txt`, `robots.txt`, `sitemap.xml`: a plain-text summary for AI assistants, the crawler rules, and the list of public pages (the home page only).
- `scripts/test-seo.cjs`: the checks for the page.
- `PRODUCT.md`, `DESIGN.md`: the positioning and the design rules the copy and the visuals follow.

The demo is a replica of the Mac app's interface driven by simulated agents. It runs in the page and does not start any agent. The window has the app's workspace switcher: Universal (My Work, Workspaces and Calendar across workspaces, with the Calendar's Timeline), Individual (this computer, with three projects) and a made-up Team called Northwind, labelled early access. Everything in the sidebar opens. my-app is the project the walkthrough drives: it starts with only its finished history, and Salie builds the rest. api-server and marketing-site are full of work of their own (boards, calendars, Git, runs, their own Archive) and are read only: what would change them, such as Start or Merge, says so in a note. api-server's waiting question is live. Each Individual project has Overview, Board, Calendar, Git, Runs and its own settings page; the board's Agent and Priority filters work, and Archive Done tasks, the Archive and Restore work in my-app. Analytics has the app's four views (Activity, Execution, Usage, Completion) and filters over ninety days of example history per project, with today's real work from the board added on top; the Team has its own Analytics. Adding anything is turned off, except through the walkthrough: New task, Add project, Add a phone, Add a Team and the like say so. Comments on a Team ticket still work. Salie has no text box: visitors pick from predefined messages, and each one gets a reply written in advance. A reply can carry generated interface (OpenUI blocks: figures, a chart, a table that sorts and filters) and proposed changes, which wait for a confirmation, one by one or with Confirm all. Salie can also suggest what to do next: at most two suggestions, each with Why this, Useful, Not useful and Dismiss, and a collapsed Memory sources list that cites the scripted records under Settings, Individual memory. A suggestion only opens a place; it starts nothing. Salie can also create a personal workspace (the app's 4.72 generative workspaces). The demo has two examples, each over one collection of its own, and each made the same way: Create with Salie in the sidebar offers its request, and Salie answers with a card that has a read only preview of the interface and saves only on Confirm. In Individual it is "Create a weekly to-do list" (Weekly to-dos: tasks with a due date and a priority, shown in Universal and Individual). In Northwind it is "Create a team follow-up tracker" (Team follow-ups: what the person is waiting on from teammates, with a teammate for each; shown in Northwind only, and private to the person, as the app says: "Team display keeps them private to you", with a read only Team projects list below the page). The app does not share generated workspaces yet (its docs defer sharing and collaboration), so the Team example is a personal workspace shown in a Team, never one teammates can see or edit. Salie draws the page and never reads or changes the records. The saved workspace is listed under Create with Salie in every workspace it is shown in, and it is a real page: a checklist, progress and status panels, a chart and a table over one collection, drawn as the app now draws them (bordered panels, a shaded filter band over each list, more room between sections). Records can be added, ticked off, edited, filtered, sorted and deleted. Customize with Salie changes the layout as a new revision (the records stay), and the ... menu has Name, icon & locations (Universal, Individual, the Team), Remove from this location, Definition history (restore as a new revision) and Delete workspace… with the reviewed keep-or-delete-data step. The Personal data library lists what a deleted workspace left behind, to inspect or reuse. Create with Salie is not offered in the Universal sidebar (a workspace is made for Individual or a Team), as in 4.73. The phone (4.73) opens workspaces and works with their records: the Control Deck lists every workspace under Workspaces, wherever it is shown on the computer, with Create with Salie (hidden during the walkthrough until a workspace exists, as the app hides it during onboarding), a workspace can be a deck button (from the page's Add to Control Deck or the Add a button sheet, into the ninth position, and "Your Control Deck is full" if Find Bugs holds it), the page has Back, Edit with Salie and no management menu or data library, and a table reads as labelled cards. Both simulators read the same workspace, so a change on one shows on the other; a workspace deleted at the computer leaves a "Removed workspace" button on the deck that can be removed. The names follow the app: the sidebar lists My Work, Workspaces and Calendar in Universal, a workspace's own home is Workspace, its board column is In progress, and the bottom of the sidebar has Settings and Devices & Hosting. Settings is one screen for Universal, Individual and a Team, and every section is filled in with an example setup: Appearance (the theme), Alerts, Task defaults, Routing rules, Time format, Runners, Agents, This computer, Phones (one is paired), GitHub (a sample account is connected), MCP services (none yet; a switch chooses between using a service in werkbord and letting a client use werkbord, and pasting one server's JSON configuration fills in a connection to review, or says why it cannot, as the app does), and Individual and Team memory, where one record can be proposed to the Team and approved by its exact text; the Team has Labels, Devices, Workspace Hosts, Connectivity, MCP clients, Backups and License. Devices & Hosting is a page of its own, listing this computer and the Team it hosts. Help is a button in the window's bottom right corner (and on the phone's deck) that opens the app's own guides (nine, including Setting up an MCP server, which opens its settings), with search. The theme switch is in the rail.

The demo moves as the app does (`docs/MOTION.md` in the product repository; the product's `web/src/lib/motion.ts`, `internal/uipresentation/static/motion.js` and `web/src/lib/mark-motion.ts` are the references). Motion connects an action to its result and never delays it, and a first paint replays nothing. The simulators repaint with `innerHTML`, so `demo-motion.js` works in pairs: it takes a snapshot of the keyed cards and layers (`data-mk` for a card, `data-mp` for the list it is in, `data-surface` for a layer) before a repaint and animates the difference after it, only when what the lists show has really changed (`revSig()` in `app-demo.js`); a different page, a filter or the theme only sets a new baseline. What moves: a card that changes column travels over 240 ms (a floating copy, inert and invisible to the guide) while its neighbours settle over 200 ms; a new card arrives over 180 ms and one that leaves fades where it stood over 160 ms, on the Individual and Team boards, the Workspace and Workspaces lists, Reviews, My Work and the deck; a card that lands in Done is acknowledged where it lands. A task panel, a sheet and its backdrop arrive over 220 ms and leave over 180 ms, once, not on every repaint. Salie shows the pixel mark at 24 px next to what it is doing (the line opens to the stages reported so far); each reply uses the next of the six approved studies (DNA helix, travelling wave, orbital braid, infinity current, pixel relay, domino cascade), fixed for that reply, capped at 30 fps and paused offscreen; only the words that have just arrived fade in (120 ms). Stop stays pending for a moment while the mark settles back, then the reply says Stopped and keeps what was written; nothing proposed is offered. Scrolling up, or selecting text, stops the conversation following the tail, and New response below returns to it over 180 ms. Analytics bars grow from their baseline (480 ms for the daily chart, 420 ms for comparisons, 280 ms when the scope changes); the daily chart is inspected with the mouse, a tap or the keys (Left and Right, Home and End, Escape), its readout floats, and every day is in the Daily values table. Fetch and Push in Git show a bounded arrow and a thin current while the request is out, with no percentage; a result keeps this computer's side and the remote's side apart, and only a result the remote confirmed gets a drawn check. Push opens a sheet that asks first, and the fetch and push answers come from a script. On the phone, moving a card to Review or merging it offers View in Review or View in Done in the notice, which stays for six seconds; saving the deck, and each stage a workflow reports, are acknowledged on the pencil and on the banner. Under reduced motion, or in a hidden page, nothing moves: labels, numbers and results are already there, and the marks stay at rest. What the demo leaves out on purpose: Salie has no text box, so there are no attachments; the deck has no edit mode that swaps keys; analytics, Git and the deck are scripted.

An invitation over the demo invites visitors to start the walkthrough or explore independently. It says what werkbord is in two short paragraphs: a meta-harness, a layer between you and all of your agents, where each agent is a harness around a model and werkbord coordinates them in one workspace (tasks, Git branches and memory together, each agent in its own worktree, nothing merges until the person says so); then Salie and the walkthrough. Only the demo controls are disabled while it is open; the waitlist stays usable. Dismissing it leaves the demo usable with no tutorial highlights; Start walkthrough in the demo bar starts it later. The choice is remembered for the browser tab. The guided story is a set of quiet notes, not a lock. Each note is one step: it names where the visitor has to be, what to press and how to tell it is done (the `STORY` list in `app-demo.js`). The note shows the first step that is not done, so clicking around never breaks it, and when the visitor is elsewhere it points at the next control on the way. The order is planning with Universal and Salie, then running two agents in Individual. While they work, schedule the third task and handle the Team board (the board has four columns, Available, In Progress, Review and Done, with no Backlog; claim a ticket, which goes straight to In Progress and waits there until Start agent; read the comment that mentions you; sign off a review). A ticket opens in the app's layout: description, requirements, the agent (a teammate sees only whether it is active), comments, and a side column with status, dates and Git. Return to the agent's question, inspect Git while it tests, then review and merge. The last chapter, Make it yours, has Salie build a workspace twice (`genSteps` in `app-demo.js` makes the six steps of each: Create with Salie, the request, Confirm on the card, Open, add the first record with its form filled in, and a note on where the records live), once in Individual and once in Northwind; the visitor then returns to Universal. The chapters are Plan, Run, Review and Make it yours, and the story ends with a skippable look at Settings. The chapters in the bar can be skipped; a skipped part makes what it would have made. Desktop and phone share the core story and the Salie conversation, including a reply that is still streaming. A switch carries the place over: the project, section, task, open sheet and Salie. A round trip with no move on the other surface returns to exactly where the visitor was, even to a place the other surface has no match for, and a workspace switcher left open on the desktop is open again. On the phone a step accepts the equivalent place, such as my-app's own board or Git tab, instead of sending the visitor back to the deck. The phone offers Individual and Team under Projects, with a compact Team board and reviews. The core story ends with Restart and Phone demo (on the phone, See what's special on the phone). That second lesson covers only what is different on the phone. It opens on the deck and its Workspaces list: what Salie built on the computer is on the phone too (if the visitor made nothing there, the lesson starts with both examples and a few records, as if made earlier). The visitor opens one, ticks a record off (switching to the Desktop view shows the same workspace with that record ticked) and sees Edit with Salie; renaming, history and deleting stay on the computer. The deck has eight navigation keys and an empty ninth, whose library lists the product's six workflow buttons; only Find Bugs works in the demo. The added key wears the accent and shows a bug icon and its name only (where it runs is in its settings and is read out to a screen reader, as in the app). A tap asks for a repository and runs; a hold (or Shift+F10) opens its settings, where a saved repository makes the next tap run straight away. While the paired computer scans, the lesson visits Team under Projects, then opens the report, which the desktop window shows too. Hide a note with its cross, and bring it back with Show tip. A note takes the place that covers the least of the app: it reads the text and controls on show, scores the places around its target by what it would cover and how far it is, never covers a ring, and keeps still until the step changes or something gets in its way. A visitor can drag a note out of the way.

Each ring is drawn in the overlay's own coordinates from the visible part of its target, with the target's corner radius, and stops where the phone's tab bar floats over the page. The guide scrolls a target into view, sideways too, and brings it back when the layout pushes it out (the note docked above a phone grows, say), but not when the visitor scrolled it away.

Rich Salie replies take about 22 seconds: text streams first, then individual metrics, chart bars, table rows or proposed changes arrive in sequence. Proposals become confirmable when generation finishes. Agent phases take 29–33 seconds, with another 26–30 seconds after answering a question. Find Bugs reports four stages over 32 seconds. The agents and Find Bugs run at 75% of the original durations (`PACE` in `app-demo.js`), and Salie's replies at 64% (`ASK_PACE`, 15% quicker again). The calendar shows seven days from the visitor's own today, so tomorrow is always on screen. A pop-up note stays up for 2.6 seconds plus 32 ms per character, up to 9 seconds. Desktop and phone use the same task clock and state; changing views does not restart a run. Agent and workflow progress pauses when the demo is offscreen or the page is hidden. Reduced motion keeps the same durations and uses larger text chunks. Restart cancels pending Salie work and resets both simulators.

## Run it locally

```bash
python3 -m http.server 8000
```

Then open <http://localhost:8000>.

## Check it

```bash
node --test scripts/test-seo.cjs
```

The tests cover the headline, title and description, the structured data, the sitemap, `llms.txt`, local links, and house rules (no em dashes, no unverified claims).

## Publish

GitHub Pages serves the `main` branch from the repository root (Settings → Pages → Deploy from a branch). Links are relative, except the canonical URLs, the share tags, `sitemap.xml`, `robots.txt` and the 404 page, which use the project path `https://micho8cho93.github.io/werkbord-site/`. If the site moves to its own domain, replace that path everywhere (`grep -rl micho8cho93.github.io/werkbord-site`), update `sitemap.xml`, and submit it to search engines.

## The waitlist

The form talks to a separate Supabase project, `werkbord-waitlist`, through three database functions (`POST /rest/v1/rpc/<name>` with the `apikey` header only):

- `join_waitlist` signs up an email. Joining again with the same email returns the same position.
- `waitlist_status` returns a returning browser's position. The browser remembers its code in `localStorage` (`wb-wl-code`).
- `waitlist_counter` returns the number of the first 50 places taken.

The page collects an email and, optionally, the team size (2, 3, 4, 5 or 6+). The team size is stored in the existing `team_size` column as `team of 2` to `team of 6+`; a blank answer is stored as null. A visit with `?ref=<8 hex>` stores the invite code in `localStorage` (`wb-wl-ref`) and sends it with the signup, but the page does not show invite links.

- The key in `assets/js/waitlist.js` is a **publishable** key and is meant to be public. Never put the `service_role` or a secret key in this repo.
- The table is not readable from the browser: row level security is on with no policies, and `anon` has no table privileges.
- Read the list as the owner, in the Supabase SQL editor: `select email, created_at from public.waitlist_signups order by created_at;`

## Keeping the copy true

- State only what ships today. Planned work appears once, labelled as planned, and never in the headline, title or description.
- No em dashes in public copy.
- Do not call the beta free unless the owner confirms it.
- `assets/img/og.png` is the share image. This repo does not regenerate it, so update it by hand when the headline changes.
