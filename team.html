One board for the team.
Your own machine for the work.

Werkbord Team is a shared workspace: who is on the team, which projects exist, one board of tickets, and the branches and pull requests that come out of them. It coordinates. It never runs anything on anyone’s computer.

The console, running in this page.

Act as Ada, Bo or Cy. Claim tickets, submit them, review them. The rules are the real ones, and they push back.

Switch who you act as: Bo is not on the Docs project, so for Bo it does not exist. Cy cannot sign off their own work. Nobody can mark a ticket done while its pull request is open.

Coordinates. Never executes.

Every developer keeps their own computer, runner, Git and agent credentials. Team holds none of them and has no way to reach yours.

No process

The server has no code path that starts a process, and an architecture test keeps it that way. Team’s build cannot even link the code that runs agents, commands or Git.

No credentials

A repository address may not contain a password or token. Each member signs in to Git with their own. Tokens are shown once, and only their SHA-256 is stored.

Metadata only

Branches, commits, pull request state, changed file names. No file contents, no diffs, no field that could carry a path on your machine. Reviewing and merging happen on your Git host.

Reported, not discovered

Team cannot look at a repository. Each member’s own Werkbord reports what it sees, and every line says “as last reported by”.

From ticket to done.

Five stages, one table of legal moves. Anything else is refused with a message that says what the ticket is and what it can do.

  1. BacklogIdeas and drafts. Anyone on the project can add one.promote
  2. AvailableReady to be taken. Claiming is atomic: exactly one person gets it.claim
  3. In ProgressOne holder, one branch named wb-142-fix-cart-total.submit
  4. ReviewA reviewer decides. Authors cannot sign off their own work.complete
  5. DoneOnly once the pull request is merged on the Git host and recorded.reopen
claim → branch wb-142-authentication-error → work and commit locally → push → open a pull request → submit → reviewer reviews and merges on the Git host → done
Nothing forces you through it. Team never merges.

Roles are lists of permissions.

Authorization asks “may this member do X”, never “is this member an Owner”. Whoever creates a project owns it, and the workspace owner owns every project.

workspace roles: owner · memberproject roles: owner · reviewer · member
Permissions by project role

Two people at once can’t break it.

Writes are serialised by SQLite, and every guard is also in the SQL. A claim reaches another member’s open console in well under a second.

Claiming

One guarded UPDATE … WHERE status = 'available' AND assignee_id IS NULL. Of any number of simultaneous claims exactly one succeeds. The rest get a 409 naming the holder.

Edits

Every write bumps a version. Saving with a stale version is refused instead of overwriting someone else’s change.

Merged is merged

A merged pull request cannot be reported back to open by a slow client, and two tickets cannot claim one branch.

Invites

The check and the use are one statement, so a single-use invite cannot be spent twice. A code that never existed, expired or ran out all answer the same 404.

Staying in step

A long-poll sync with a revision and an event cursor. A console that was offline reloads what it missed and says so while the connection is down.

Conflict awareness, not conflict solving.

The Repository tab assembles what members’ Werkbords reported and ranks what needs a human, worst first.

conflict

An open pull request the Git host says has merge conflicts.

behind

A developer’s branch is behind its base branch.

overlap

Two active branches change the same files, so whoever merges second may get conflicts.

merged

The pull request is merged and the ticket can be marked Done.

stale · closed · leftover · orphan

No activity for 14 days, a pull request closed unmerged, a finished ticket’s branch to delete, a branch no ticket is linked to.

Bring people in with a link.

A project owner makes an invite: a role (member or reviewer, never owner), a number of uses and a number of days. The link is shown once. Only its hash is stored.

Make an invite to see the link. This is an example, nothing is created.

Start a workspace.

One computer hosts the server. Everyone else just opens its address in a browser and signs in with their own token.

  1. Add everyone from the Workspace tab. Each person gets their own token, shown once. Send it privately.
  2. Let teammates reach it behind HTTPS (Caddy, nginx) or on a VPN or tailnet. Team serves plain HTTP and says so.
  3. Each person keeps working in their own Werkbord, and runs werkbord-team handoff to bring a ticket they hold into it.
